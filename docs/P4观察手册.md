# P4 观察手册：模型是否真的走 apply_plan

> 目的：P4 删掉 3 个读工具后，确认（a）没有残留调用（b）建图确实收敛到 `apply_plan`
> 数据源：`public.agent_tool_invocations`（字段见 `agent-core/.../entity/AgentToolInvocation.java`）
> 时间窗：部署 P4 之后至少跑 1 个完整画布任务

---

## 1. 最该先看的一条：有没有残留调用

被删的 3 个工具如果还被调用，表现是 `Tool not found`（工具不在注册表），会以错误状态落库。

```sql
-- 残留调用检查：P4 之后这些工具名应该 0 行
SELECT tool_name, status, COUNT(*) AS calls, MAX(started_at) AS last_seen
FROM public.agent_tool_invocations
WHERE tool_name IN (
        'canvas_graph_get_context',
        'canvas_graph_list_nodes',
        'canvas_graph_list_edges')
  AND started_at >= :deploy_time
GROUP BY tool_name, status
ORDER BY calls DESC;
```

**判读**：0 行 = 干净；有行 = 技能或提示词里还残留引导（去查 `canvas-design` / `canvas-run` / `turn-context`）。

---

## 2. 建图是否收敛到 apply_plan

```sql
-- 每个会话里"建图类"工具的调用分布
SELECT tool_name, COUNT(*) AS calls,
       COUNT(DISTINCT conversation_id) AS conversations
FROM public.agent_tool_invocations
WHERE tool_name IN (
        'canvas_graph_apply_plan',
        'canvas_graph_create_node', 'canvas_graph_create_nodes',
        'canvas_graph_create_edge', 'canvas_graph_create_edges',
        'canvas_graph_import_media', 'canvas_graph_import_media_batch',
        'canvas_graph_update_node',
        'canvas_graph_mark_result_slots',
        'canvas_graph_layout_graph')
  AND started_at >= :deploy_time
GROUP BY tool_name
ORDER BY calls DESC;
```

**判读**：

| 结果 | 含义 |
|---|---|
| `apply_plan` 占绝大多数 | 收敛成功，可以删旧工具 |
| `create_nodes` / `create_edge` 仍高频 | 模型仍在走"逐节点建图"，要么技能引导不够强，要么 `apply_plan` 报错逼它降级 |
| `apply_plan` 大量 `status='error'` | 先修 `apply_plan` 易错点，**别急着删旧工具**——删了就没有退路了 |

---

## 3. 每轮调用次数的前后对比（收敛收益的直接度量）

```sql
-- 每个 turn 里画布工具调用次数：P4 前 vs P4 后
WITH per_turn AS (
    SELECT conversation_id,
           tool_call_id,
           COUNT(*) FILTER (WHERE tool_name LIKE 'canvas_graph_%') AS canvas_calls,
           COUNT(*) FILTER (WHERE tool_name = 'canvas_graph_apply_plan') AS apply_plan_calls,
           MIN(started_at) AS turn_at
    FROM public.agent_tool_invocations
    WHERE tool_name LIKE 'canvas_graph_%'
    GROUP BY conversation_id, tool_call_id
)
SELECT CASE WHEN turn_at >= :deploy_time THEN 'after' ELSE 'before' END AS phase,
       COUNT(*) AS turns,
       ROUND(AVG(canvas_calls), 2) AS avg_canvas_calls_per_turn,
       ROUND(AVG(apply_plan_calls), 2) AS avg_apply_plan_per_turn,
       MAX(canvas_calls) AS worst_turn
FROM per_turn
GROUP BY phase;
```

**判读**：`after` 的 `avg_canvas_calls_per_turn` 应明显下降。若没降，说明模型在重试 / 走多步，收敛没实际生效。

## 4. apply_plan 的失败原因分布（决定能不能继续删）

```sql
-- apply_plan 报错的具体原因，决定 P5 是否安全
SELECT error_code, LEFT(error_message, 120) AS message, COUNT(*) AS calls
FROM public.agent_tool_invocations
WHERE tool_name = 'canvas_graph_apply_plan'
  AND status <> 'success'
  AND started_at >= :deploy_time
GROUP BY error_code, LEFT(error_message, 120)
ORDER BY calls DESC
LIMIT 20;
```

**判读**：若 `PLAN_INVALID` 集中在"ref 写错 / mediaId 与 url 都传 / resultSlots 与 media 冲突"这几类，
说明模型还没吃透 `apply_plan` 的契约——**此时删掉 `create_node` 等简单工具是危险的**，
因为模型失去了"简单但能成功"的退路。

---

## 5. 决策门槛（写死，避免凭感觉）

满足以下**全部**才继续 P5：

- [ ] §1 残留调用 = 0 行
- [ ] §2 `apply_plan` 调用数 ≥ 其他建图工具之和
- [ ] §3 `avg_canvas_calls_per_turn` 相比 before 下降
- [ ] §4 `apply_plan` 成功率 ≥ 90%

任一条不满足 → **停**，先修技能引导或 `apply_plan` 易用性，不动工具集。

## 6. 快速替代：临时埋点（不改表结构）

不想等 `agent_tool_invocations` 落库时，可直接从 MoonAgent 日志捞：

```powershell
# 在 MoonAgent 日志里统计画布工具调用
Select-String -Path MoonAgent/logs/*.log -Pattern 'canvas_graph_\w+' |
  ForEach-Object { ($_.Line -split 'canvas_graph_')[1] -replace '[\s",].*','' } |
  Group-Object | Sort-Object Count -Descending |
  Select-Object Count, Name
```

`SkillExpander` 启动时也会打 `[SkillExpander] 发现本地工具: <name>`，可据此确认工具注册面。
