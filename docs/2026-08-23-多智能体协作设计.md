## 0. 术语与边界（先钉死概念）

- **编排（orchestration）** = 控制面：节点/边/路由/状态/恢复，决定谁、何时、按什么顺序跑。迁移前现状 = `PlanGraph`（StateGraph）。
- **规划（planning）** = 目标 → 子任务序列。现状 = 意图识别 + 各 handler 内部生成方案。
- **专才 Agent** = 一个**有界自主循环**：自己的 `ChatClient` + 自己的 `@Tool` 工具面 + 自己的记忆 + 明确的终止条件（maxSteps/deadline/幂等/预算）。**核心是新概念**——现有 handler 是**确定性工作流**（无循环、无自主决策），要升格为 agent 才能被「派发」。
- **多智能体协作** = 一个协调者把目标拆成子任务，**动态**派发给多个专才 agent，回收结果并汇总。强调「动态决策找谁」；静态预设连线（C3）不在此列。

> 结论：现状是「单智能体 + StateGraph 控制流 + 4 模型角色 + 工具」，**不是多智能体**。做 C1/C2 的本质 = 把 handler 升格为 agent，再加一个能拆解、派发、汇总的协调者。

---

## 1. 目标与不成文约束

**目标**：让 AI 能把「复杂业务目标」拆解，交由多个专才 agent 分工完成，并保持**可靠、可治理**。

**必须保留的现状契约（红线）**：
1. **用户满意再执行**——HITL 人工确认卡片的哲学不变。
2. **SSE 事件协议**（`workflow/message/human_input/video_plan/task_accepted/message_end/error` + `models/recommended/reasons`）不变，前端零破坏。
3. **异步长任务形状**（生视频 `task_accepted` + 轮询）不能被吃满墙钟。
4. **会话级互斥锁**（`ConversationLock` Semaphore）防重入。
5. **checkpoint 一次性消费 + 过期**（resume 语义不变）。
6. **上游错误 LLM 友好化**，不裸抛给用户。

## 2. 两种形态总对比

| 维度 | C1 主管拆解 + 每子任务人工确认 | C2 主管自主派发专才 |
|------|-----------------------------|--------------------|
| 谁决定拆解/派发 | 主管 agent 拆解，**每子任务给用户确认**后再派 | 主管 agent 自主拆解+派发，用户不逐个确认 |
| 与 HITL 哲学 | **完全一致**（人工参与每个关键决策） | 部分冲突（主管自主决策，仅最后结果确认） |
| 确定性 | 高（人工把关每一步） | 低（主管自由行动） |
| 新增复杂度 | 中 | 高（预算/幂等/终止/失败回滚/审计全要） |
| token 成本 | 中（解构确认多轮） | 高（自主循环多轮，工具失败重试） |
| 适用 | 复杂分镜/多素材生产（生成类，长任务） | 分析/规划/短任务（文本聚合），生成类慎用 |
| 风险 | 低，可逐子任务回滚 | 高，一个子任务失败可能拖死整链 |

**推荐**：先生成类链（aisplit/pic/video）走 **C1**；纯文本分析/综合走 **C2**。二者共用同一套「专才 Agent + 子任务 + 派发 API」底层，只是协调者决策带不带人工确认的差别。

## 3. 共同基础层（C1/C2 共用）

### 3.1 专才 Agent 抽象（新）

把一个业务子能力封装成一个可被派发的 agent：

```java
public interface SubAgent {
    String name();                 // agent_pic / agent_aisplit / agent_video / agent_review ...
    String description();          // 给主管 LLM 看的「此 agent 能做什么」
    List<String> capabilities();   // 能力标签，供规则/LLM 匹配
    // 有界循环入口：传入子任务上下文，返回结构化结果；失败不抛异常，返回错误对象
    SubAgentResult run(SubTaskContext ctx);
}
```

- **实现形态**：每个 `SubAgent` = 一个「子任务专用 ChatClient」（text/vision 由 `AgentNodeClients` 工厂造）+ 自己的工具子集（从 `AgentTools` 挑 writeScenes/replaceScenes/refineImage/generateVideo/deleteScenes）。
- **替代/共生**：现有 `IntentHandler` 不动，`SubAgent` 是给「派发」用的新壳；`SubAgent` 内部可复用 handler 的钩子（runHITLStage / resumeStage / StagePlan），避免两套逻辑。

### 3.2 子任务数据模型（V6 migration，落地 C1 需要）

用户优先级「用户提交 > LLM 推荐 > checkpoint plan > config」不变；子任务本身需要落库，才能跨重启恢复、审计、逐子任务回滚。

```sql
-- agent_subtasks：一次协作派发的子任务（一个 supervisor 一轮拆解 = 1 行 parent + N 行 child）
CREATE TABLE agent_subtasks (
  id               VARCHAR(64) PRIMARY KEY,
  conversation_id  VARCHAR(64) NOT NULL,
  parent_id        VARCHAR(64),            -- 父任务（被拆解的 subtask）
  agent_name       VARCHAR(64) NOT NULL,   -- 派给哪个专才 agent
  goal             TEXT NOT NULL,          -- 子目标（user-facing，中文）
  status           VARCHAR(16) NOT NULL DEFAULT 'pending', -- pending/running/done/failed/cancelled
  result           TEXT,                   -- 子 agent 返回的结果（JSON 文本）
  error            TEXT,
  plan             TEXT,                   -- 子任务方案（复用 checkpoint 语义，可空）
  params           JSONB,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX idx_subtasks_conv ON agent_subtasks(conversation_id, created_at DESC);
```

> 注：`agent_checkpoints.form_token` 已承担「一次性确认 + 过期 + 方案存 JSON」职责。C1 的**子任务确认**可复用 checkpoint 表（子任务确认 = 一次 HITL checkpoint），或用 `agent_subtasks.status + form_token` 引用同一张 checkpoint 行。二选一，见 §4.4 决策点。

### 3.3 派发 API（service 层）

```java
public interface SubTaskDispatcher {
    // 发一个子任务到对应专才 agent（异步：virtual thread 有界循环），立即返回 taskId
    String dispatch(OrchestrationRequest req, SubTaskSpec spec);
    // 轮询子任务状态（供前端 + supervisor 回收）
    SubTaskStatus status(String conversationId, String taskId);
}
```

- **执行**：虚拟线程 `CompletableFuture.runAsync(..., agentExecutor)`，有界循环内自持 `SubTaskContext`（goal / params / refImages / 目标 projectId / sceneId）。
- **并发**：子任务间**可并行**（不同专才、无共享写状态），用 `CompletableFuture` allOf；**同场景写库冲突**用现有场景锁/事务兜底。supervisor 拆解阶段串行，派发阶段并行。

### 3.4 有界循环收敛条件（强制，缺一不可）

每个专才 agent 的循环必须自带，否则一个子任务失败拖死 supervisor：

| 条件 | 实现 |
|------|------|
| maxSteps | 默认 3（工具调用轮数上限） |
| 墙钟 deadline | 文本 60s / 视觉 120s / 图 180s / 视频沿用 task_accepted+轮询（不阻塞） |
| 幂等键 | goal + 源分镜集合的 hash，写库前查重 |
| 终止条件 | 重复状态 / 无进展 / 工具被拒 / 畸形输出 / 预算耗尽 → 正常返回错误对象 |
| 工具异常 | @Tool 内 try-catch 返回错误对象（不抛）——沿用「工具异常被吞」现状红利 |
| 审计 | `SimpleLoggerAdvisor` + 子任务落库（§3.2），每步可回溯 |

### 3.5 错误处理

- 子任务失败 → `SubAgentResult.error`，**不外抛**；supervisor 决定：a) 换一个 agent 重试 / b) 回滚已成功子任务 / c) 降级为「请人工补充」HITL 卡片 / d) 汇总失败原因给用户（LLM 友好化）。
- 已成功子任务的回滚：写库类（分镜）走 replaceScenes 同事务语义；生图/生视频类通过「删除对应资产行 + 状态复位」实现（不真是物理删除上游产物，是业务回滚）。

## 4. C1 详细设计（主管拆解 + 每子任务人工确认）

### 4.1 PlanGraph 增量（只在 run 路径加节点，resume 基本不动）

```
intent_recognize（现有）
  └─ 低置信度 → intent_clarify（现有）
  └─ 高置信度 + 目标复杂（规则：多意图复合 / 关键词「一次帮我…」/ 上一轮 supervisor 拆解结果仍在）
       → node_supervise
  └─ 高置信度 + 目标简单 → 现有 handler 节点（零改动，无感知）

node_supervise：supervisor（text 模型）把原需求拆成 N 个子任务 JSON
  → 每个子任务发给用户确认（复用 runHITLStage → human_input 卡片，
     actions = 各子任务的「确认派发 / 跳过 / 自定义」+ ✍ 自定义输入）
  → 用户勾选 → resume_route 按子任务逐条派发

→ 子任务全部完成后：node_reconcile 汇总（text 模型合并各子结果）→ 最终 message_end
```

- **新增**：`node_supervise`、`node_reconcile`、以及「逐子任务派发」的 handler 适配节点（或复用现有 node_* 作为「子任务执行节点」，见 §4.2）。
- **切链出口**：resume 路径已支持 `routingHint` 显式切链 + `customText` 重识别，无需另建。
- **新 intent**：可加 `intent-supervise`（当规则判定「复合目标」时命中），走 `SuperviseIntentHandler`；或复用现有 intent-other 的 handler 内部分支判定——推荐前者（一个 handler 一种职责，符合「新增意图 = 新类 + @Component」）。

### 4.2 子任务执行怎么映射到现有节点

最省事：`SuperviseIntentHandler` 用 `SubTaskDispatcher.dispatch()` 把每个已确认子任务发给对应专才 agent，**不新增 N 个节点**——专才 agent 内部是独立有界循环，不占用主管图节点。主管图只保留 `node_supervise`（拆解+收集确认）与 `node_reconcile`（汇总）。这样节点数少、resume 条件边几乎不用动。

### 4.3 SSE 事件协议扩展（前端增量，不破坏既有）

复用现有事件 + 一个可选事件：

- `workflow{title:"拆解任务", status:node_started/node_finished}`（拆解进度）
- `human_input{...}`：子任务确认卡片（action 数组 = 各子任务确认项 + `custom`）
- 逐子任务派发进度：`workflow{title:"正在执行「生成分镜」", ...}`（不新增事件，用 workflow 即可）
- **可选新增** `subtask{taskId, agentName, status, goal}`：给前端渲染「子任务正在执行」状态列（更清晰）；**若不愿动前端协议，可用 workflow 替代**（零前端改动）。

### 4.4 子任务确认：复用 checkpoint vs 新表

- **倾向**：复用 `agent_checkpoints` 做「子任务确认单」——每子任务一个 `form_token`（一次性消费 + 30min 过期 + plan 存子任务 JSON），与现有 HITL 完全同构，前端 `HumanInputCard` 零改造。`agent_subtasks` 只记执行状态/结果，不重复做确认。
- **若勾选多子任务**：一次 human_input 卡片带多子任务 → 拆成多个 checkpoint（一卡多 token）或一个 checkpoint + 一个 `subtaskIds` 数组。推荐后者（一次确认，逐条派发）。

### 4.5 C1 时序（分镜生成 + 配图为例）

```
user: "帮我做一个 5 镜头的科幻分镜，并给每个镜头配一张图"
→ intent_recognize: 规则命中复合目标 / LLM→intent-supervise
→ node_supervise: supervisor 拆解
   [1] 生成分镜脚本(5镜头)  → agent_aisplit
   [2] 每个镜头生图          → agent_pic (×5, 依赖[1])
→ human_input 卡片: [确认派发全部 / 只做[2] / 自定义]
→ 用户勾选确认 → resume_route → 逐子任务 dispatch（[1]串行 → [2]并行）
→ workflow 进度 + 子任务执行 → node_reconcile 汇总 → message_end
```

## 5. C2 详细设计（主管自主派发专才）

### 5.1 supervisor 是一个有界循环（不是 StateGraph 节点）

C2 的主管本质是**自循环 agent**：

```java
// supervisor loop（抽象）
SupervisorResult supervise(goal, ctx):
  for step in 1..MAX_SUPERVISOR_STEPS:
     plan = llm(goal, 当前状态, {agent 描述列表})        // text 模型，结构化输出
     if plan 已含最终答案: return plan.final             // 主管自己回答（分析/规划类）
     for task in plan.subtasks:
        result = dispatcher.dispatch(task)               // 派专才，同步等待（短任务）
        if result.failed: 回滚已成功子任务 + 打终止条件    // 或换 agent
        state += result
  return 超限错误（LLM 友好化）
```

- **为何不进 StateGraph**：C2 的子任务数量/类型是**运行期决定**的，图要静态预知节点集；用 supervisor 循环天然支持任意维度。图适合 C1（确定性的「拆解→确认→派发」骨架）。
- **模型**：主管 = text（mimo-v2.5，超时 120s，`memoryClient()`）；专才按能力选 text/vision/image/video。

### 5.2 预算 / 幂等 / 终止（C2 硬要求）

- **预算**：总 token 上限（主管+子任务合计，硬编码或 config）；子任务数上限（如 ≤5）；超限直接收敛出「已做部分 + 建议人工继续」。
- **幂等**：子任务 goal+输入 hash 作幂等键，写完库查重；重复派发同一子任务拒绝。
- **终止**：连续 2 轮无进展 / 无工具产出 / 子任务全部失败 → 终止并友好化。
- **失败策略**：子任务失败不静默——回滚已成功写库项，把失败原因给用户（LLM 翻译），建议补人工或换表述。

### 5.3 C2 的适用边界（纪律）

- **只给短任务/纯文本**：意图识别、分析/综合、方案建议、检索汇总。
- **生成类（生图/生视频/写分镜）禁区**：异步长任务 + 用户要满意才执行 + 会吃满墙钟。这些必须走 C1（人工确认后才派）。
- 判断依据可由 supervisor 在拆解时给每个子任务打 `async: bool` 标签：`async=true` → 强制转 C1 人工确认；`async=false` → 可自主执行。

### 5.4 C2 SSE 演进

- supervisor 自主循环：`workflow` 事件逐子任务播报（无需新增事件）。
- 每子任务完成：`message` 增量播报「已完成 X」+ 结果摘要（打字机）。
- 最终 `message_end` 带完整汇总；若走 C1 边界（async 子任务），转为 `human_input` 确认卡片 + 后续 resume。

## 6. 模型路由（专才 agent 用什么）

| 专才 agent | 主模型 | 工具面 |
|-----------|--------|--------|
| agent_aisplit（分镜脚本） | text（mimo-v2.5）+ vision（理解现有分镜/参考图） | writeScenes / replaceScenes |
| agent_pic（图片） | vision（看图改图提示）+ image（gpt-image-2） | refineImage / 文生图 |
| agent_video（视频） | vision（出方案）+ video（MiniMax-H3） | generateVideo（task_accepted+轮询） |
| agent_review（分镜查看/评审） | vision + text | 只读分析，无写库 |
| agent_delete（删除） | text | deleteScenes |
| supervisor | text（拆解+汇总） | 无（通过 dispatcher 间接调专才） |
| reconcile | text（合并各子结果） | 无 |

路由仍经 LLM 网关（`model_params.is_default` + 每能力模型列表），与前文「4 类模型角色」一致；专才只是**按需**复用对应模型/工具，不新增上游。

## 7. 演进路线与迁移

1. **Phase 0**：抽 `SubAgent` 抽象 + `SubTaskDispatcher`（含虚拟线程有界循环）+ 收敛条件；选 1-2 个现有 handler 升格为 agent（如 agent_pic、agent_aisplit）——纯底层，行为不变，先立骨架。
2. **Phase 1（C1）**：加 `intent-supervise` handler + `node_supervise/node_reconcile` + 子任务确认卡片（复用 checkpoint）→ 复合目标能拆解+人工确认+逐条派发。**先落 C1**（低成本、不违哲学）。
3. **Phase 2（C2）**：supervisor 自主循环 + 预算/幂等/终止；仅对文本/短任务开放；`async` 子任务强制回落 C1。
4. 全程红线：SSE 协议、checkpoint 语义、会话锁、异步视频形状、错误友好化——零回归。

> 迁移建议：**先 P0+P1（C1）**，跑通「复合目标→拆解→人工确认→并行派发」闭环，再评估要不要开 C2。C2 的不确定性（token/长任务/回滚）风险显著高于 C1，不建议一步到位。

## 9. 未做（YAGNI / 暂时搁置）

- **C3 StateGraph 子图**：静态连线、协作弱，除非确需「预定义固定协作拓扑」，否则 C1 的派发 loop 更通用。需要时再补。
- **agent 互相直接调（peer handoff）**：依赖 supervisor 层做收敛；直接 peer 调会失去「汇总/人工把关」，token 和失控面都更大。C2 用够了，暂不单独做。
- **跨会话/跨项目 agent 编排**：所有子任务仍绑定 `conversation_id + project_id` 归属校验（延续现状红线）。
