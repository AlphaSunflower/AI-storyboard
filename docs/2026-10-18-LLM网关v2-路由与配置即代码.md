# LLM 网关 v2：路由、渠道池与配置即代码

> 落地日期：2026-10-18
> 迁移：`AILLMGateway/src/main/resources/db/migration/V20__gateway_routing_v2.sql`（其他环境需手动执行）
> 目标：把「模型 → 渠道」的静态绑定，升级成可负载、可回退、可覆盖、可观测、可导入导出的路由层。

---

## 1. 能力总览

| 能力 | 行为 |
|---|---|
| 多渠道负载 | 同模型多路由按 `priority` 分层，同层内按 `route.weight × channel.weight` 加权随机（无放回） |
| 故障切换 | 429 / 5xx / 超时换下一个候选；业务 4xx 直接透传 |
| 重试 | 路由/渠道 `max_retries` 控制额外尝试（上限 3），可跨 Key 重试 |
| 冷却 | Key 失败进入本机冷却（429=30s、401/403=120s、5xx=15s、连续 5 次=300s） |
| 上游模型映射 | `route.upstream_model` 覆盖请求体 `model`；空=同名直发 |
| 参数覆盖/删除 | `route.param_overrides` 支持 `set` / `setIfAbsent` / `delete`，支持点路径 |
| 跨模型回退 | 主模型全部候选失败后，按 `model_fallback.sort_order` 依次尝试，最多 2 层 |
| 多 Key 池 | 一个渠道可挂多个 Key，加权轮换、单 Key 冷却；池为空回退 `channel.api_key` |
| 可观测 | `call_log` 记录上游模型、第几次尝试、prompt/completion/total tokens；`/admin/metrics` 聚合渠道/模型成功率、P95、Token |
| 配置即代码 | 整份配置导出为 YAML；校验后按名称 upsert 导入；导出不含 Key 明文 |

---

## 2. 数据模型（V20）

```sql
-- 渠道运行参数
channel: weight, timeout_ms, max_retries, last_error, last_checked_at

-- 路由升级为「部署」
model_route: enabled, priority, weight, upstream_model, timeout_ms,
             max_retries, param_overrides

-- 多 Key
channel_key(id, channel_id, label, api_key(AES), weight, enabled,
            fail_count, cooldown_until, last_used_at, ...)

-- 跨模型回退
model_fallback(id, model_name, type, fallback_model, sort_order, ...)

-- 可观测
call_log: upstream_model, attempt, prompt_tokens, completion_tokens, total_tokens
```

`model_route` 增加 `(model_name, channel_id)` 普通索引；管理端创建/改目标时校验重复，
存量重复行不阻断编辑（历史数据里已有重复，编辑其中一条不会被另一条卡死）。

## 3. 选路算法

```
resolve(model, forcedChannelId):
  routes = model_route[model] 且 enabled
  for route: channel = channel[route.channel_id] 且（非强制测试时）enabled
  去重（同渠道只留一条）
  按 (route.priority, channel.priority) 升序分层
  每层 weightedShuffle(weight = route.weight × channel.weight)
```

请求循环：

```
for candidate in candidates:
  for attempt in 1..(1 + maxRetries):
    key = keyPool.select(channel)          # 池为空回退 channel.api_key
    body = merge(requestBody, candidate.param_overrides, candidate.upstream_model)
    resp = adapter.forward(body, channel, key, timeout)
    if 2xx: log(success, upstream_model, attempt, usage); return
    log(error, upstream_model, attempt)
    if 429/5xx: markKeyFailure; continue
    else: return resp                      # 业务 4xx 不重试
if depth < 2: for fallback in model_fallback[model,type]: retry with fallback
return 50301
```

强制渠道（管理端「测试这一行」）会跳过 enabled 过滤，只测该行本身的配置。

## 4. 参数覆盖

`param_overrides` 示例：

```yaml
param_overrides:
  set:                 # 强制覆盖调用方
    response_format: url
    style.type: photo
  setIfAbsent:         # 调用方没传才补
    watermark: false
  delete:              # 渠道不支持，删除
    - prompt_optimizer
    - style.weight
```

- 支持点路径；数组下标不支持。
- 兼容历史 `default_params`：如果 JSON 没有 `set/setIfAbsent/delete` 任一键，整个对象按 `set` 处理。
- 顺序：先 `delete`，再 `setIfAbsent`，最后 `set`；最后写 `model`（上游映射优先级最高）。
- 解析失败时按原始 body 透传并 `log.warn`，不会把正常请求打死。
- 文本采样参数（temperature/max_tokens/top_p）仍由调用方决定；需要渠道差异时用 `setIfAbsent`。

**限制**：图改图（`/v1/images/edits`）是 multipart 字节流，当前只复用选路/权重/Key 池，
不做上游模型名与参数覆盖的字节改写；需要时走单独的 multipart 重写适配器。

## 5. 多 Key 池

- `channel_key.api_key` 与渠道主 Key 使用同一 AES 算法，管理端永不回显明文。
- 选择：`enabled` Key 中跳过冷却，按 `weight` 加权随机；全部冷却时仍尝试一个（避免整渠道不可用），并告警。
- 失败冷却：429=30s、401/403=120s、5xx=15s、其他错误=60s；连续 5 次至少 300s。
- 成功即清除冷却与失败计数。
- 冷却状态存在本机内存（当前单实例）；多实例部署时替换为 Redis 即可，接口不变。
- 视频创建/轮询/下载、聊天/生图、图改图都会走 Key 池。

## 6. 配置即代码（YAML）

### 6.1 格式

```yaml
version: 1
channels:
  - name: laozhang
    type: openai_compatible
    base_url: https://api2.laozhang.ai/v1
    enabled: true
    priority: 0
    weight: 2
    max_retries: 1
    models: [deepseek-flash, gemini-3-flash-preview]
    keys:                       # 只导出元数据，不含 Key
      - label: key-1
        weight: 1
        enabled: true
models:
  - name: doubao-seedream-4-0-250828
    type: image
    schema:                     # 等价于 params_schema，YAML 对象
      request:
        - key: size
          label: 尺寸
          type: enum
          options: [1K, 2K, 4K]
          default: 2K
      response:
        sync:
          dataPath: data
          mediaField: b64_json
          fallbackField: url
    params:                     # 固定列（snake_case，可只写需要覆盖的）
      context_window: 128000
      sizes: 1K,2K,4K
      size_default: 2K
      n_min: 1
      n_max: 15
      n_default: 1
    routes:
      - channel: 豆包生成
        upstream_model: doubao-seedream-4-0-250828
        enabled: true
        priority: 0
        weight: 3
        max_retries: 1
        is_default: true
        param_overrides:
          set:
            response_format: url
          delete: [watermark]
    fallbacks: [doubao-seedream-5-0-flash-260915]
```

### 6.2 导入语义

- 按名称 upsert：渠道按 `name`，Key 按 `channel + label`，模型参数按 `(name, type)`，路由按 `(model, channel)`。
- **不删除** YAML 里没有的配置；要下线用管理端删除/停用。
- `fallbacks` 是全量替换；`[]` 表示清空。
- Key 安全：导出不含 `api_key`；导入时已有 Key 不写 `api_key` 则保持不变，新 Key 必须在 `keys[].api_key` 提供明文，否则跳过并告警。
- 渠道新建时若没有 `api_key` 且不是 Ollama，会报错；请先用管理端创建渠道，或在 YAML 里提供 `api_key`。
- 导入前会先校验：YAML 语法、渠道引用、重复模型/类型、每个模型只能有一个 `is_default`、Schema 结构、参数覆盖结构。
- 缓存：导入走现有 Service，渠道/路由/参数变更会触发现有模型目录缓存失效。

### 6.3 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/admin/config-yaml` | 导出整份配置 YAML（无密钥） |
| POST | `/admin/config-yaml/validate` | `{yaml}` → `{valid, errors[], warnings[]}` |
| POST | `/admin/config-yaml/import` | `{yaml}` → 导入计数 + warnings |
| POST | `/admin/model-params/schema/convert` | `{content, from: json\|yaml}` → `{json, yaml}` |

管理端新增「配置即代码」页：载入当前配置、下载 YAML、校验、应用导入。
路由弹窗的 Schema 支持「转 YAML / 转 JSON」，保存/校验前自动转回 JSON。

## 7. 可观测

`/admin/metrics`（近 7 天）：

```json
{
  "window": "7d",
  "channels": [{"channelId","channelName","calls","success","errors",
                "successRate","avgMs","p95Ms","tokens","lastError"}],
  "models":   [{"model","calls","success","errors","successRate","avgMs","p95Ms","tokens"}],
  "tokensToday": {"promptTokens","completionTokens","tokens"},
  "tokens7d":    {"promptTokens","completionTokens","tokens"}
}
```

- 每次尝试都落一条 `call_log`（含失败与重试），因此渠道健康度能反映真实失败率。
- Token 从同步响应 `usage` / Gemini `usageMetadata` 提取；流式请求目前不解析 token（避免影响 SSE 透传）。
- 管理端仪表盘新增「今日 Token」「渠道健康」「模型延迟与 Token」；渠道「最近错误」取 call_log 最近一条失败。

## 8. 管理端改动

- **模型路由列表**：模型/上游、优先级/权重、启停、默认、覆盖规则、创建时间。
- **编辑路由**：上游模型名、优先级、权重、重试、启停、回退模型、参数覆盖行编辑器（set/setIfAbsent/delete）、Schema YAML/JSON 切换。
- **渠道**：权重、超时、额外重试、Key 池（添加/启停/删除，Key 只写不读）。
- **配置即代码**：独立页面，YAML 导入导出。
- **仪表盘**：Token、渠道健康、模型 P95/Token。

## 9. 已知限制 / 后续

1. **图改图** multipart 不做上游模型/参数改写（选路与 Key 池已统一）。
2. **视频跨模型回退**未实现：视频创建失败会切同模型其它渠道，但不换模型（换模型会改变任务语义与下载来源）。
3. `UpstreamClient` 内部仍有全局 429/5xx 重试（`gateway.upstream.retry-count`），与路由重试叠加；
   需要精确控制时把全局重试设为 0，只保留路由 `max_retries`。
4. Key 冷却在内存，多实例需换 Redis。
5. 配置导入不删除、不做 prune；需要「声明式全量」时再加 `prune=true`。
6. 渠道 `last_error` / `last_checked_at` 列暂未持续写入，监控以 call_log 聚合为准。
7. 存量重复路由不会自动清理（运行时会按渠道去重）；需要时用管理端逐条删除。
