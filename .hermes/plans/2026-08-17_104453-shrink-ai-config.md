# AI 配置瘦身 + 模型语义修正 实现计划

> **For Hermes:** 用 subagent-driven-development 按任务逐步实现（每任务一个 fresh subagent + 双重 review）。

**Goal:** 把主后端 `application.yml` 里臃肿的 `ai.laozhang.*` 默认模型/默认参数段瘦身到最小，并修正「MiniMax 挂在 laozhang 前缀下」的语义错误——MiniMax-H3 实际走网关 minimax 渠道直连 MiniMax 自家网址（`{base}/v2/video_generation`），与 laozhang 中转站无关。

**Architecture（已核实）:** LLM 网关（AILLMGateway，8083）是模型路由与参数默认值的权威源：
- `model_route` 表：modelName → channelId + type（text/image/video/vision）
- `channel` 表：baseUrl / apiKey(AES) / type(openai_compatible|gemini|minimax) / priority / enabled
- `model_params` 表：每模型能力枚举 + 默认值（size_default / duration_default / resolution_default / aspect_ratio_default / n_default / quality_default …），经 `/v1/models?type=X` 下发
- 视频：`VideoGatewayServiceImpl` 按 model 查 route → channel，`minimax` 渠道 → 直连 MiniMax 自家 `/v2/video_generation`；`veo-*` → laozhang `/videos`。网关内部已兜底 resolution=768P（application.yml `default-resolution`）、duration=8、ratio=16:9、size=1280x720。

主后端 `AiConfigProperties`（prefix `ai.laozhang`）仍持有一批**重复的**默认模型名 + 默认参数，属冗余状态。

**Tech Stack:** Spring Boot 4 / MyBatis-Plus / Lombok；前端 React 19 + TS（前端静态兜底列表在 `config.ts`，本次不动）。

## 现状 vs 目标（application.yml 的 ai 段）

现状（8 个 key，全在 `ai.laozhang` 下）：
```yaml
ai:
  laozhang:
    minimax-video-model: MiniMax-H3
    gemini-image-models: gemini-3-pro-image-preview
    video-model-aliases: '{"veo-3.1-fast":"veo-3.1-fast-generate-preview",...}'
    default-image-model: gpt-image-2
    default-image-edit-model: gpt-image-2
    default-vision-model: gemini-3-flash-preview
    default-image-size: "1024x1024"
    default-video-duration: "8"
    video-upload-dir / video-file-extension / video-url-prefix   # 文件存储，保留不动
```

目标（`ai.laozhang` 段整体消失；默认模型平铺到 `ai.*`，5 个 key）：
```yaml
ai:
  agent:
    intent-threshold: 0.6
    max-clarify-rounds: 2
    max-regenerate-rounds: 3
  # 兜底默认模型（网关 /v1/models + model_params 为权威源；仅调用方未显式传模型时兜底）
  image-model: gpt-image-2              # 文生图 + 图改图共用（合并 default-image-model / default-image-edit-model）
  vision-model: gemini-3-flash-preview  # 脚本生成/看图理解/提示词优化共用（合并 default-vision-model / default-understanding-model）
  video-model: MiniMax-H3               # 视频默认模型（MiniMax 直连自家，非 laozhang 中转；原 minimax-video-model）
  # 模型路由提示（前端卡片过滤 / veo 别名；网关 model_route 为权威路由）
  gemini-image-models: gemini-3-pro-image-preview
  video-model-aliases: '{"veo-3.1-fast":"veo-3.1-fast-generate-preview","veo-3.1-fast-fl":"veo-3.1-fast-generate-preview","veo-3.1":"veo-3.1-generate-preview","veo-3.1-fl":"veo-3.1-generate-preview"}'
```

删除的 key（共 5 个默认参数/模型）：
- `default-image-edit-model` → 并入 `image-model`（当前二者同为 gpt-image-2）
- `default-understanding-model` → 并入 `vision-model`（代码里默认值同为 gemini-3-flash-preview，yml 本就未写）
- `default-image-size` → 内联常量 `"1024x1024"`（`normalizeImageSize` 兜底参数）
- `default-video-duration` / `default-video-resolution` / `default-video-size` / `default-video-aspect-ratio` → 全删，未显式传值时透传 null，由网关兜底（768P/8s/16:9/1280x720，与现默认值一致）

保留不动：`video-upload-dir` / `video-file-extension` / `video-url-prefix`（文件存储，与模型无关）。

## 风险 / 权衡 / 待确认

1. **`video-model-aliases` 与 `gemini-image-models` 是否还能删**（本次保留，属路由提示非「默认模型」）：
   - `video-model-aliases`（veo 简称 → 实际名）——前端现已从网关 `/v1/models` 拿实际模型名，`getOrDefault(alias, alias)` 对已传实际名时是幂等透传。需确认是否还有路径传「veo-3.1」简称（scene.videoModel 历史数据 / LLM 推荐值）。若无非简称路径 → 可删。
   - `gemini-image-models`——PicIntentHandler 用它把 Gemini 生图模型从「图改图(edits)」卡片过滤掉（Gemini generateContent 不支持 /images/edits multipart）。这是真实行为，但本质是重复了网关「哪些模型是 gemini 渠道」的知识。彻底解法是网关 `/v1/models` 增加 per-model `vendor`/`supportsEdit` 字段 → 属网关改造，另行评估。
2. **是否把「默认模型」也下沉网关**：网关目前 `model_route`/`model_params` 无「默认模型」标记，故后端仍需保留 image/vision/video 三个兜底名。若要彻底单一权威源，需给网关加 per-type 默认模型（model_params 加 `is_default` 或新表），后端改为启动时/调用时拉取。这是较大改造，**本次不实施**，是否要做请用户定。
3. **prefix `ai.laozhang` → `ai`**：已确认 `application-local.yml`/`application-prod.yml` 无 `ai.laozhang` 覆盖（只覆盖 `ai.gateway`），故改 prefix 不破坏 profile。但 `ai.agent.*` 是否由独立 bean 绑定需在 Task 2 一并确认（AiConfigProperties 无 agent 字段，不会冲突）。
4. **`default-image-edit-model` 合并**：当前与 `default-image-model` 同为 gpt-image-2，合并零损失。若未来图改图要独立模型，再拆出 `image-edit-model` 字段即可（YAGNI）。
