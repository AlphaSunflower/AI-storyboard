# LLM 网关评审：模型路由、渠道管理与「编辑路由」重设计

> 评审对象：`AILLMGateway`（:8083，Spring Boot 4）
> 对照产品：LiteLLM、new-api（one-api 系）、Higress AI 网关、OpenRouter、Cloudflare AI Gateway
> 结论口径：先修「会误导人」的假旋钮/假测试，再补运行时治理能力；不建议一上来做语义缓存和计费体系。

---

## 0. 摘要（先看这 8 条）

1. **`model_route.default_params` 是死字段**：创建/更新写库、列表展示、VO 回传，但请求链路从不读取。界面上的「默认参数（JSON）」改了不起任何作用。
2. **路由「测试」测的不是这一行的渠道**：`POST /admin/routes/{id}/test` 只拿 `modelName` 走通用路由，实际会打到该模型优先级最高的渠道。在第二条路由上点测试，结果可能来自第一条。
3. **路由只做「顺序 + 失败换下一个」**：没有权重、没有冷却/熔断、没有退避重试、没有跨模型回退，也没有「上游模型名」映射（公共名必须等于上游名）。
4. **删渠道不检查路由**：逻辑删除后路由仍指向已删渠道，列表显示「未知渠道」，请求直接 50301；也没有任何影响面提示。
5. **参数 Schema 只能手写 JSON**：只有前端 `JSON.parse` 校验；结构错了静默退化成固定列；`response` 归一化映射在界面上完全不可见；**保存后无法清空**（空值被当成「不修改」）。
6. **「默认值」有三个来源互相打架**：路由 `default_params`（死）、`model_params` 固定列的 `*_default`（只下发不注入）、`params_schema.request[].default`（前端真正用的）。同一个模型在 Agent 和画布可能渲染出不同的字段与默认值。
7. **参数按「模型 + 类型」全局共享**，编辑任意一条路由的参数会改掉该模型在所有渠道上的表现，但界面没有任何作用域提示。
8. **同一模型的 text / vision 双类型在 `/v1/models` 只会出现一个**：`putIfAbsent(modelName, type)` 按名字去重，另一个类型被丢掉；`model_params` 明明是按 `(model_name, type)` 存的。

## 1. 现状盘点（带证据）

### 1.1 对象模型

当前只有四张主表，语义都很「薄」：

| 表 | 当前语义 | 主要缺口 |
|---|---|---|
| `channel` | 上游供应商：`type / base_url / api_key / priority / enabled / models(CSV)` | 单 Key、无权重、无超时/重试/额外头、无健康状态、`models` 只是候选提示不参与校验 |
| `model_route` | 「模型名 → 渠道」绑定行，带 `type / default_params / is_default` | 无 `enabled`、无权重、无上游模型名、无覆盖参数、无回退；`default_params` 不生效 |
| `model_params` | 按 `(model_name, type)` 存能力枚举与默认值 + `params_schema` | 与 schema 双写、默认值三处来源、字段无法清空 |
| `gateway_api_key` | 业务调用 Key（仅开关） | 无额度、无模型白名单、无限流、无到期 |

`model_route` 没有 `(model_name, channel_id)` 唯一约束（V1 只有普通索引），同模型同渠道可以重复建行，候选列表里会出现同一渠道两次。

### 1.2 路由解析链路

`GatewayRoutingServiceImpl.route()` 的实际步骤：

1. 从请求体取 `model`；
2. `select * from model_route where model_name = ?`（每次请求都查库）；
3. 逐行 `selectById(channel)`，过滤 `enabled`，按 `is_default desc, channel.priority asc` 排序；
4. 顺序尝试，429/5xx 换下一个，其余 4xx 直接透传。

由此带来的具体问题：

- **没有负载均衡**：`priority` 小的渠道吃掉全部流量，其余渠道只在故障时被动接管。多渠道配置的实际收益只有「故障切换」，不是「分摊」。
- **没有冷却**：被打挂的 429 渠道下一次请求仍排第一，每个请求都要先撞一次限流再切换，延迟和错误率被放大。
- **`is_default` 语义混用**：它本意是「该类型的默认模型」，却被拿来给候选渠道排序。同一个模型的默认路由会无条件压过其它渠道的优先级设置。
- **没有上游模型映射**：`modelName` 同时是公共名和发给上游的名字。想给业务一个稳定别名（例如 `image-default`）而让不同渠道各自映射到 `seedream-4.0` / `gpt-image-2`，当前做不到；只能让业务直接使用上游名。
- **没有路由级开关**：下线一个模型只能删路由（丢配置）或停整个渠道（连带该渠道其它模型）。
- **类型不校验**：`route.type` 是手填的，和渠道协议、`model_params.type` 都没有交叉校验，可以存出「text 模型指向 gemini 图片渠道」这种配置。
- **目录折叠**：`fetchModels()` 用 `modelTypeMap.putIfAbsent(modelName, type)`，一个模型名只能保留一个类型；`model_params` 支持的同名 text/vision 两套参数在目录里只剩一套。
- **N+1**：候选渠道逐行 `selectById`，图片请求还会额外查一次 `model_params`。QPS 上来后应改为「路由表缓存 + 版本号」（复用 `ModelCatalogCache` 的思路）。

### 1.3 渠道管理

- **单 Key**：轮换 Key 只能编辑渠道覆盖，没有「多 Key 轮询 / 失败跳过」。
- **优先级无权重**：`priority` 是严格顺序，不是分组权重。
- **无自动禁用**：`call_log` 已经记录了失败，但没有连续失败阈值、冷却时间、自动恢复。
- **删除无守卫**：`ChannelServiceImpl.delete()` 直接逻辑删除，不检查是否仍被路由引用。
- **`models` 是 CSV**：只用于模型下拉候选和测试弹窗，建路由时并不校验模型是否在该渠道列表里，拼错也能保存上线。
- **无渠道级超时/重试/额外 Header/额外 Body**：全局 `gateway.upstream.*` 一刀切，遇到需要 `api-version`、`anthropic-beta` 或固定 `response_format` 的上游只能改代码。
- **两个「测试」都不是端到端**：
  - `POST /admin/channels/{id}/test` 直连上游，绕过了网关的类型适配与响应归一化，只能证明「Key 和网络通」；
  - `POST /admin/routes/{id}/test` 走网关，但不锁定该路由的渠道（见摘要第 2 条）。

### 1.4 参数、默认值与 Schema

**(a) 三个默认值来源**

| 来源 | 存在形式 | 谁在用 | 问题 |
|---|---|---|---|
| `model_route.default_params` | 路由行上的 JSON 文本 | **没人用** | 纯装饰；更新时只在非 null 时写，**清空也清不掉** |
| `model_params.*_default`（`size_default` / `duration_default` / ...） | 固定列 | 经 `/v1/models` 下发，由前端/Agent 自行读取 | 网关不注入；与 schema 冲突时无仲裁 |
| `params_schema.request[].default` | Schema 内 | `AgentParamSelector`、画布 `modelConfig/generationPanel` | 有 schema 时 Agent 完全忽略固定列，画布却会把固定列里 spec 未声明的字段合并进来（还可能把 type 改写成 enum）→ **同一个模型两端渲染出的字段集合不同** |

**(b) 保存语义：清空等于没改**

`ModelParamsServiceImpl.applyNonNull()` 只在字段非 null 时赋值。前端保存时把空输入序列化成 `null`：

```js
req.paramsSchema = schemaText ? schemaText : null;   // app.js
```

于是 **Schema 一旦保存过，界面上删空后保存不会删除**；`sizes`、`durations`、默认值等同样只能设不能清。路由的 `defaultParams` 也是同一模式。

**(c) Schema 是「半成品编辑器」**

设计文档 [agent-model-param-schema-design.md](agent-model-param-schema-design.md) 里 M7 要求「Admin schema 编辑器 + JSON 一键导入」，实际落地是：

- 一个 12 行 textarea；
- 一个「从请求体 JSON 一键生成」按钮（`prompt()` 粘贴 JSON，猜类型）；
- 一个「填入示例」按钮；
- 保存前只做 `JSON.parse`。

它既不是表单，也不是校验器，更看不到 `response.sync/async` 这一段真正决定「上游响应能不能被归一化」的映射。字段说明只覆盖 `options/min/max/show`，`role`、`cardinality`、`stateMap`、`mediaMode`、`dataPath` 全靠猜。

**(d) Schema 非法时静默降级**

`ModelParamsSpecNormalizer.spec()` 解析失败返回 `null`，调用方退回固定列或直接透传上游响应，**没有日志、没有告警、界面上也看不出来**。配置错了只会表现为「图片显示不出来 / 视频一直 processing」。

### 1.5 「编辑路由」弹窗逐项体检

| 控件 | 实际行为 | 问题 |
|---|---|---|
| 渠道 | `route.channel_id` | 停用渠道灰显但可选可保存，保存后请求直接 50301 |
| 模型类型 | `route.type` | 与渠道协议、`model_params.type` 无交叉校验 |
| 模型 | `modelName` + datalist | 无「上游模型名」；同名多渠道时无法区分上游命名 |
| 默认模型 | `route.is_default` | 兼做候选排序；靠代码清标记，无 DB 约束，并发可出两个默认 |
| 参数配置 | 30+ 个固定滑块 | 作用于 `model_params(model_name,type)`，**所有渠道共享**；切换类型时 `innerHTML` 重建，**已填值全部丢失** |
| 本地模型 | `ollama_params` | 只对 Ollama 有意义，混在通用弹窗里 |
| 默认参数 JSON | `route.default_params` | **不生效**、无补全、无类型校验、清空无效 |
| 参数 Schema JSON | `model_params.params_schema` | 手写、无结构校验、无预览、清空无效、`response` 段不可见 |
| 保存 | 先 PUT 路由，再 PUT 参数 | 非原子：参数保存失败只 `console.warn`；Schema 非法时路由已经保存成功，用户看到报错但配置已半截生效 |

此外：

- 无重复校验（同模型同渠道可建多行）；
- 无搜索/筛选/分页（模型上百后表格不可用）；
- 无「复制路由」「批量建路由（模型 × 渠道矩阵）」；
- 无脏数据离开提醒；
- 列表没有显示上游模型名、权重、健康度、最近错误。

**差距归纳为四类**：

1. **表达力**：路由只是绑定行，表达不了「权重、上游名、覆盖参数、开关、超时、重试」；
2. **运行时**：没有冷却/熔断/回退，多渠道退化成「主备」；
3. **配置体验**：Schema 与默认值是手写 JSON，且作用域、优先级、清空语义都不清楚；
4. **可观测**：日志只够看总量，不够定位「哪个渠道、哪次重试、哪个上游模型、花了多少 token」。

## 3. 目标设计

### 3.1 先拆对象：Model / Route / Channel / Key

```
Model（公共模型，业务只认它）
  ├─ name, type, icon, 能力/参数 schema, 默认参数, 是否该类型默认
  └─ Route[]（部署 = 模型 × 渠道）
        ├─ channel_id, upstream_model, enabled, priority, weight
        ├─ timeout_ms, max_retries, fallback_model
        └─ param_overrides（仅本路由，set/delete）
Channel（上游供应商）
  ├─ type, base_url, priority, weight, enabled
  ├─ timeout_ms, max_retries, extra_headers, extra_body
  ├─ health（Redis：失败计数、冷却截止、最近错误）
  └─ Key[]（多 Key 轮询/加权）
```

关键变化：

- **`default_params` 升级为 `param_overrides`**：只对本路由生效，语义是「set / delete」，不是一整坨 JSON；
- **`is_default` 从路由行上移**：它是「模型 + 类型」的属性，不是「模型 × 渠道」的属性；
- **参数 Schema 归 Model**，Route 不再携带能力配置；
- **健康状态放 Redis**，DB 只存配置，避免每次请求写库。

### 3.2 路由解析算法

```
resolve(model, body):
  routes = enabledRoutes(model)                 # 带缓存 + 版本号
  if empty: 40401
  tiers = groupBy(routes, priority).asc
  for tier in tiers:
    pool = tier.filter(not coolingDown)
    while pool not empty:
      r = weightedPick(pool); pool.remove(r)
      body2 = merge(body, r.param_overrides)    # set/delete
      try:
        resp = adapter(r.channel.type).call(
                 upstreamModel = r.upstream_model ?? model,
                 timeout = r.timeout_ms ?? channel.timeout_ms ?? global,
                 body = body2)
        on 2xx: recordSuccess(r); return resp
        on 429/5xx/timeout: recordFailure(r, maybeCooldown); continue
        on other 4xx: return resp               # 业务错误，不重试
      catch: recordFailure; continue
  if fallbackChain(model): return resolve(fallback, body)   # 深度 ≤ 2
  return 50301 with per-attempt errors
```

要点：

- **同优先级按权重随机**（加权无放回），天然兼顾负载与故障切换；后续要 least-latency 再加 EWMA，不必改协议。
- **冷却中的路由直接跳过**，全部冷却时返回 429 + `retryAfter`，而不是硬打。
- **参数合并顺序**：调用方显式 > 路由覆盖 > 模型默认 > 上游默认。文本采样参数（temperature/max_tokens/top_p）保持调用方所有，网关不注入，延续现有约定。
- **合并只作用于图片/视频与显式配置的字段**，避免突然改变文本行为。

### 3.3 数据模型（DDL 草案）

```sql
-- 路由升级为「部署」
ALTER TABLE model_route
  ADD COLUMN enabled BOOLEAN NOT NULL DEFAULT TRUE,
  ADD COLUMN priority INT NOT NULL DEFAULT 0,
  ADD COLUMN weight INT NOT NULL DEFAULT 1,
  ADD COLUMN upstream_model VARCHAR(128),
  ADD COLUMN timeout_ms INT,
  ADD COLUMN max_retries INT,
  ADD COLUMN param_overrides TEXT,          -- JSON；迁移自 default_params
  ADD COLUMN fallback_model VARCHAR(128);

CREATE UNIQUE INDEX uk_route_model_channel
  ON model_route(model_name, channel_id) WHERE deleted = FALSE;

-- 默认模型独立成表（每类型一行），替代 model_route.is_default / model_params.is_default
CREATE TABLE model_default (
  type VARCHAR(32) PRIMARY KEY,
  model_name VARCHAR(128) NOT NULL,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- 渠道运行参数
ALTER TABLE channel
  ADD COLUMN weight INT NOT NULL DEFAULT 1,
  ADD COLUMN max_retries INT NOT NULL DEFAULT 0,
  ADD COLUMN timeout_ms INT,
  ADD COLUMN extra_headers TEXT,
  ADD COLUMN extra_body TEXT,
  ADD COLUMN auto_disable_threshold INT,
  ADD COLUMN last_error TEXT,
  ADD COLUMN last_checked_at TIMESTAMPTZ;

-- 多 Key
CREATE TABLE channel_key (
  id VARCHAR(64) PRIMARY KEY,
  channel_id VARCHAR(64) NOT NULL REFERENCES channel(id),
  api_key TEXT NOT NULL,                    -- AES
  weight INT NOT NULL DEFAULT 1,
  enabled BOOLEAN NOT NULL DEFAULT TRUE,
  cooldown_until TIMESTAMPTZ,
  fail_count INT NOT NULL DEFAULT 0,
  last_used_at TIMESTAMPTZ
);

-- 观测补齐
ALTER TABLE call_log
  ADD COLUMN upstream_model VARCHAR(128),
  ADD COLUMN attempt INT,
  ADD COLUMN prompt_tokens INT,
  ADD COLUMN completion_tokens INT,
  ADD COLUMN cost NUMERIC(12, 6);
```

> 迁移顺序：先加列并双写 → 业务切读新列 → 再删 `default_params` / 两个 `is_default`。不要一步到位改语义。

```
│                                        [取消]  [保存并测试]        │
└───────────────────────────────────────────────────────────────────┘
```

#### Tab 1「绑定」

- 渠道下拉带健康度、优先级、启停、当前路由数；停用渠道不可选（或强提示）。
- 模型名与上游模型名分离；上游名默认等于公共名。
- 类型由「模型参数配置」推导，手改时提示冲突（渠道协议 / `model_params.type` / 已有路由）。
- 「设为默认」旁边直接显示「当前默认：xxx」，避免两个默认并存。
- 保存前做三件事：重复校验（模型+渠道）、渠道可用性校验、必填校验。

#### Tab 2「参数与默认值」

把「参数定义（Schema）」和「默认值」合并成一张表，一行一个参数：

| 列 | 控件 | 说明 |
|---|---|---|
| 键 | 输入框 | 上游请求体键名，支持 `style.style_type` 点路径 |
| 显示名 | 输入框 | Agent / 画布上的 label |
| 类型 | 下拉 | enum / range / number / bool / string / object / array / arrayofobject |
| 选项 / 范围 | 动态 | enum → 标签式多选；range → min/max/step；number → 无 |
| 默认 | 动态 | 与类型匹配的控件 + 「不发送」开关（三态：未设置 / 默认透传 / 强制覆盖） |
| 展示 | 开关 | `show:false` = 有默认值但不进 UI |
| 高级 | 折叠 | `role`（image_upload/reference/response）、`cardinality` |
| 操作 | 拖拽 + 删除 + 复制 | 顺序即渲染顺序 |

- 「从请求体导入」保留，但改为弹窗内解析 + 逐行可改，不再用 `prompt()`。
- 「校验」调用服务端，错误定位到具体行与字段；有错误时禁用保存。
- 「JSON 视图」双向同步，给高级用户逃生口。
- 右侧预览直接按 Agent / 画布的真实规则渲染一遍（enum 下拉、range 滑块、bool 开关、object 分组），做到「所见即所配」。

**默认值的继承关系要显式化**：

```
调用方显式值  >  路由覆盖（set/delete）  >  模型默认（schema.default）  >  上游默认
```

每行显示「生效值」，以及它来自哪一层；冲突时（固定列与 schema 默认不一致）标黄并提供「以 schema 为准 / 以固定列为准」的一键收敛。

#### Tab 3「响应映射」

这一段现在完全不可见，却是「图片不出 / 视频一直 processing」的根因。建议做成分组表单 + 试运行：

```
同步响应（图片/文本）            异步响应（视频）
dataPath        [data      ]     taskIdPath   [task_id     ]
dataIsArray     [✓]              statusPath   [status      ]
itemsAreUrls    [ ]              stateMap     pending → queued
mediaField      [b64_json  ]                  processing → running
fallbackField   [url       ]                  success → succeeded
stripDataUri    [✓]              mediaPath    [video_url   ]
errorPath       [error.message]  mediaMode    [直链 ▾]
                                 downloadPath [content     ]
                                 timeoutSec   [300         ]

[粘贴一段真实上游响应]  [试运行归一化]  →  {taskId, status, url, error}
```

「试运行」直接调用后端新增的预览接口，复用 `ModelParamsSpecNormalizer`，让配置者在保存前就能看到归一化结果。这比任何文档都有效。

#### 保存语义

- **原子**：路由、参数、Schema 一次事务提交，任何一段失败都不落半截。
- **可清空**：请求体区分「字段未提供」与「显式置空」，前端用 `null` + `clearFields: []` 或 PATCH 语义；至少对 `paramsSchema`、`sizes`、`*_default` 提供清空。
- **脏检查**：切换 Tab / 关闭弹窗时提示未保存；切换类型不重建 DOM，先收集现值再按新类型映射，无法映射的字段显式提示「已丢弃」。
- **保存并测试**：保存成功后自动用「锁定本路由渠道」的测试端点跑一次，结果直接显示在弹窗底部。

#### 路由列表

- 列：模型 / 上游模型 / 类型 / 渠道（健康、优先级、权重）/ 默认 / 启停 / 成功率 / p95 / 操作。
- 顶部：关键词、类型、渠道、启停筛选；分页。
- 批量：启用/停用/删除/复制到其它渠道；「按模型 × 渠道矩阵批量建路由」。
- 行内：启停开关、测试（锁定本行渠道）、复制、查看影响面。

#### 渠道页

- 卡片式：Key 数、路由数、今日调用、成功率、p95、最近错误、冷却状态。
- 编辑：权重、超时、重试、额外 Header/Body、自动禁用阈值；多 Key 管理（轮询/加权、单 Key 冷却）。
- 删除：先查影响面，有路由时返回 409 并列出模型，支持「转移到其它渠道」后再删。
- 批量测试 + 测试结果留痕（最近一次时间/耗时/错误）。

### 3.6 Schema 正式化

保留现有 mini-spec（不要引入完整 JSON Schema，收益低、迁移重），但补三件事：

1. **版本号**：`{"schemaVersion": 2, ...}`，后端按版本解析；
2. **结构校验**：键唯一、type 枚举、enum 必须有 options、range 的 `min<=max` 且 default 在范围内、object 必须有 fields、`role:image_upload` 必须有 `cardinality`、`stateMap` 的值只能是 `queued/running/succeeded/failed`；
3. **样例回归**：每个 spec 存一份 `sampleRequest` / `sampleResponse`，CI 用它们跑归一化断言；改 schema 必须同时改样例。

同时统一消费端规则：**schema 优先，固定列只在无 schema 时兜底**。画布侧目前会把固定列里 spec 未声明的字段合并进结果（`mergeField`），而 Agent 侧有 schema 时完全忽略固定列；两边要收敛成同一顺序，否则同一个模型在 Agent 与画布会给出不同的字段集合。

## 5. 回归用例（可直接落测试）

1. **权重与故障切换**：同模型两渠道权重 1:1，100 次请求分布 40–60；停用一路后 100% 命中另一路；一路 429 后进入冷却，冷却期内不再被选中，到期恢复。
2. **路由测试隔离**：同模型两条路由分别指向 A/B，测试 B 时上游只收到 B 的请求，响应里 `channelId=B`。
3. **参数覆盖**：调用方未传 `size` → 注入路由覆盖值；调用方传了 → 保留调用方；`delete` 操作后该键不出现在上游请求体。
4. **默认值优先级**：调用方 > 路由覆盖 > 模型默认 > 上游默认，四层各一条断言。
5. **Schema 校验与清空**：非法结构返回 400 + 路径；清空后保存，`GET` 返回 `null`；合法 spec 在 Agent 与画布渲染出相同控件与默认值。
6. **响应试运行**：粘贴 MiniMax 轮询样例，预览输出 `{status:"succeeded",url:"..."}`；未知状态归一到 `running`。
7. **删除渠道**：有路由时返回 409 并列出模型；`force=true` 后路由标记失效并给出提示。
8. **默认模型唯一性**：并发设置两个默认，最终 DB 与 Redis 各只有一个，`/v1/models` 标记一致。
9. **同名双类型**：同一模型同时配 text/vision，`/v1/models` 两条都在，参数分别取对应行。
10. **原子保存**：故意让参数保存失败，路由不应被写入（或整体回滚）。

## 6. 不建议现在做

- **完整 JSON Schema Draft**：现有 mini-spec 足够，换标准只会增加迁移与前端复杂度。
- **语义缓存 / 内容安全 / Prompt 攻击检测**：在路由与配置正确之前，收益远低于维护成本。
- **计费体系**：除非要对外售卖；内部使用先做 Token 统计即可。
- **重写管理后台为 React**：当前原生 JS 够用，先把信息架构和校验补上。
