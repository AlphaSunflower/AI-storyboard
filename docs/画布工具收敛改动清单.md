## 进度：已完成的改动（P0 完成，且改成了更省的方案）

原计划新增一个聚合工具 `canvas_graph_update`。实施时发现 **`apply_plan` 已支持 nodes + edges + layout 一次提交**，
缺的只是"改已有节点"与"标记已有节点为结果槽"两条能力。因此改为**直接给 `apply_plan` 补这两条**——
不新增工具，反而比原计划更彻底：`apply_plan` 成为唯一写入口。

### 改动文件

| 文件 | 改动 |
|---|---|
| `CanvasGraphCommandServiceImpl.java` | 新增 `applyNodePatch()` / `applyMarkResultSlots()` 两个内部方法；`applyPlan` 新增阶段 4c（改节点）与 4d（标记槽）；`updates` / `markResultSlots` 进增量 `patch`；`nodes` 改为可空（三者至少给一个） |
| `CanvasGraphCommandService.java` | 接口 javadoc 更新 plan 形状与新语义 |
| `CanvasGraphToolInputs.java` | 新增 `NodeUpdateSpec` record；`PlanSpec` 增 `updates` / `markResultSlots` 字段并把 `nodes` 改为可选；新增 `toUpdateMaps()` / `toMarkSlotMaps()` |
| `CanvasGraphMcpTools.java` | `apply_plan` 描述改为「建图与改图的首选，也是唯一入口」，plan 参数描述同步 |
| `canvas-design/SKILL.md` | 第 6/7/10/11/13 条改为「改图也走 apply_plan」，并明确禁止为改一个字段单独调工具 |
| `CanvasGraphApplyPlanEditTest.java` | **新增 7 个测试**：纯改图、未知 nodeId、id/type 不可改、标记槽、已有素材拒绝、建+改+标记混合单 revision、空 plan 报错 |

### 顺带消重的两处旧实现

`updateNode` 与 `markResultSlots` 两个单功能方法改为调用新 helper（不再各留一份实现），
保证「聚合入口」与「单功能工具」在收敛期语义完全一致——这一点很关键，否则 P4-P6 删旧工具时会出现行为差异。

### 一个关键验证点

`mixedPlanCreatesUpdatesAndMarksInSingleRevision` 断言了：**建 1 个节点 + 改 1 个节点 + 标记 1 个槽
= 1 个 revision（`save` 只调用一次）**。这正是收敛的核心收益——分开调 4 次工具会 reload 4 次、revision +4。

## 6. 两个必须先定的设计问题

**Q1. 聚合入口叫什么、长什么样？**
候选：`canvas_graph_update`（节点字段 + 增删边 + 设槽三合一）。
反方：三合一入口参数复杂，模型容易填错；另一种是保留 `update_node` + 单独一个 `canvas_graph_link`（只负责边和槽）。
建议按"边和槽都是**图结构**变更、节点字段是**数据**变更"来拆成 2 个，而不是 1 个三合一。

**Q2. 版本降级路径要不要保留？**
SKILL.md:22 现在教模型在 `apply_plan` 不可用时退回逐节点工具。若 P5 删掉被降级目标：
- 要么删掉降级段落（假设服务端永远同版本）
- 要么保留旧工具一个版本周期
建议：P4/P5 与 SKILL 降级段落**同批删**，并确认部署时 canvas 与 moon-agent 同版本发布。

## 7. 结论

- 本次收敛**可行且收益明确**：27 → 14，读工具的三合一用户零感知。
- 真正的成本不在删工具，而在**三张权限清单 + 两份中文标签 + 两个 SKILL.md + 六个测试文件**的同步。
- 最高风险点是 **P5 的权限清单漏登**（新入口未登记 → 落到默认策略）。
- 建议从 **P0 纯新增** 开始：加聚合入口、新旧并存、跑绿，再谈删。
